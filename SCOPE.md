# AM Radar — Scope

This document defines what AM Radar does and explicitly does NOT do. It exists
so that future expansion requests (including those generated by LLMs) can be
evaluated against a fixed boundary, not against vague aspirations.

AM Radar is a literature **discovery** layer focused on **additive-manufacturing
mechanical performance**. It is a sibling of the original Research Radar; it
reuses the same pipeline but tracks a different, AM-specific set of research
directions. The discovery / deep-parsing boundary with lit-system is inherited
unchanged.

---

## What AM Radar IS

AM Radar is a **literature discovery layer**: a daily-running, low-cost system
that scans new academic publications, scores their relevance to a fixed set of
additive-manufacturing research directions, and delivers a curated digest.

Concretely, it:
- Pulls new papers from arXiv, OpenAlex, PubMed
- Deduplicates by DOI (strict `doi:` prefixed key; no fuzzy dedup)
- Routes papers to research directions using keyword rules
- Scores each paper with an LLM (priority + bilingual summary + key terms)
- Renders a daily/weekly HTML digest at GitHub Pages
- Records every run with manifest + CHANGELOG (version governance)

Properties:
- Runs autonomously on GitHub Actions (no local machine required)
- Low operating cost (~¥0.5–2/day, DeepSeek LLM calls); cost is explicitly
  acceptable and is never a reason to cut recall
- **Corpus persistence: `data/` on the `main` branch ONLY** — never split across
  `main` + GitHub Releases, and there is no monthly-archive / release workflow
  in this repo. The full corpus is one tree on `main`.
- Versioned (config snapshots, prompt versions, model snapshots)

## Research directions

The four directions are defined in `config/directions.yaml`, which is the single
source of truth. Do not hardcode direction names or counts anywhere the code can
derive them from config.

1. **`mechanical_properties` — AM Mechanical Properties.** Tensile/yield
   strength, elongation, ductility, fracture toughness, strain hardening, and
   build-orientation / mechanical anisotropy of additively manufactured parts.
2. **`fatigue` — AM Fatigue.** Fatigue life and strength, S-N behaviour, high-
   and very-high-cycle fatigue, defect-driven fatigue, crack initiation and
   growth in AM parts.
3. **`ti6al4v_postprocess_hip` — Ti-6Al-4V Post-processing & HIP.** Hot isostatic
   pressing, heat treatment, and other post-processing of additively
   manufactured Ti-6Al-4V (porosity closure, microstructure). **"HIP" here means
   *hot isostatic pressing*, not the hip joint** — see the disambiguation in
   `decisions/ADR-0001-am-radar-scope.md`.
4. **`am_femoral_stem` — Femoral Stem (AM + traditional).** Femoral / hip stem
   design, porous-titanium and lattice stems, stress shielding, cementless and
   short stems — covering both additively manufactured and traditional stems.

Each direction routes on a strong keyword paired (in realistic papers) with an
additive-manufacturing term (additive manufacturing, selective laser melting,
laser powder bed fusion / LPBF / L-PBF, powder bed fusion, electron beam melting
/ EBM, directed energy deposition, wire arc additive / WAAM).

Per the recall-over-precision calibration (`CLAUDE.md` §1), adjacent-field and
methodologically transferable papers are valued, not filtered out.

## Source strategy — OpenAlex is keyword-first

`openalex_concepts` is **intentionally empty** for every direction;
`openalex_keywords` carries the entire OpenAlex signal.

Rationale: in the sister project, concept-id filters frequently returned more
than ~2000 results per query. The cursor-paginated fetch caps each query at a
fixed page budget, so over-cap concept queries silently dropped the overflow and
**lost papers** — a recall failure. Keyword (`search=`) queries are narrower and
stay under the cap, so keyword-first avoids that silent truncation. When a query
still hits the cap, the fetcher now raises a loud `openalex_truncated` quality
flag (see "Inherited guarantees") rather than dropping rows silently.

This is recorded in `decisions/ADR-0001-am-radar-scope.md`.

## Inherited pipeline guarantees

These behaviours come from the shared pipeline and recall-hardening work and
must be preserved:

- **Concurrent scorer** — papers are LLM-scored concurrently for throughput.
- **Score-before-dedup** ordering — scoring happens against routed candidates;
  pre-dedup against the corpus drops already-seen papers before scoring, with a
  write-time first-seen-wins safety net.
- **Retry-aware scorer** — transient LLM failures are retried rather than
  silently dropping a paper.
- **Era-split search index** — the client-side search index is split per year
  (`search-index-YYYY.json` + a manifest) to keep each file small (ADR-0022).
- **Loud zero / truncation flags (batch 1)** — a per-source `*_returned_zero`
  quality flag fires when a fetcher returns nothing, and `openalex_truncated`
  fires when an OpenAlex query hits its page cap with more results still
  available. Both surface in the run manifest / status page so silent recall
  loss is visible.
- **Data-integrity guardrails** — empty-run gate in `_save_daily`, strict
  DOI-only dedup, versioned scorer prompts (`prompts/scorer_vN.txt`, never
  overwritten), and a per-run manifest.

## What AM Radar is NOT

These are explicitly out of scope and belong to other systems (primarily
lit-system, the deep-parsing / RAG layer):

### Full-text processing
- PDF download / parsing (Docling, GROBID, pypdf, MinerU, etc.)
- OCR, equation / figure / table extraction

### Knowledge construction
- Chunking, embeddings, vector stores (Chroma, Qdrant, FAISS, …)
- Retrieval-Augmented Generation (RAG)
- Knowledge-graph or citation-graph construction
- Author / institution disambiguation beyond what OpenAlex provides

### Deep semantic operations
- Cross-paper synthesis, literature-review generation, research-gap or
  hypothesis generation, methodology recommendation

### Personalization / interaction
- Feedback loops, active learning, personalized re-ranking
- Conversational / chat-with-papers interface

### Allowed human-curation aids (client-side only)
- Reading marks and notes on the browse surface (to-read / read / interesting /
  ignore, plus free-text notes), persisted in localStorage only — no server
  state, no sync. Cross-corpus priority navigation pages
  (`high-priority.html`, etc.). These are curation aids on Radar, distinct from
  lit-system's automatic machine annotation of deep-parsed PDFs.

If a feature touches the "is NOT" list, it belongs in lit-system — reject or
redirect.

## The Radar → lit-system contract

AM Radar is the upstream **discovery** layer. lit-system is the downstream
**deep-parsing / RAG** layer.

AM Radar discovers new papers and LLM-scores their priority; it renders a daily
digest and logs run metadata. lit-system receives those candidates, deep-parses
them, builds a RAG knowledge base from the parsed content, and answers research
questions.

Interface (planned): a DOI-keyed JSONL export at
`data/exports/candidates.jsonl` that lit-system reads to ingest High/Medium
papers. No tight coupling — a file-based handoff.

The contract: Radar guarantees fresh, relevance-filtered candidates with stable
identifiers (DOI). lit-system guarantees not to push deep-parsing
responsibilities back upstream.

## Resource division of labor: GPU vs API

This boundary is **resource-aware**, not just functional. AM Radar and
lit-system may share a machine but consume different scarce resources.

- **AM Radar uses the DeepSeek API exclusively** for all LLM scoring. Its
  per-paper work is shallow but broad (a few fields, classification-grade),
  which the API handles trivially at scale. Cost (~¥0.5–2/day) is treated as
  effectively free.
- **lit-system owns the local GPU** — reserved for deep parsing, structured
  extraction, and embedding for its vector store. Its per-paper work is narrow
  but deep.

### Hard rules

- **Radar must not consume GPU.** No local model fallback, no embedding
  generation, no fine-tuning routed through Ollama or a local DL runtime.
- **lit-system must not assume API LLM access.** Its design must remain viable
  without the API (e.g. for sensitive or offline documents).
- **No silent resource borrowing.** If Radar genuinely needs GPU later (e.g. a
  re-ranker that must be local), that requires updating SCOPE.md with a
  documented exception. Default is no sharing.

These rules are enforced mechanically by `pipeline/scope_audit.py` (forbidden
imports of local-LLM / DL runtimes, forbidden local LLM endpoints).

## How to evaluate future feature requests

Ask in order:

1. Does it strengthen the discovery / scoring / digest loop? → maybe accept.
2. Does it touch any "what AM Radar is NOT" item? → reject; that is lit-system's job.
3. Does the proposer assume Radar has data it does not have (full text,
   embeddings)? → reject.
4. Does it reduce recall (tighter routing, broad negative keywords, restrictive
   `must_pair_with`)? → reject; recall is the optimization target.

A feature passes only if it strengthens the discovery / scoring / digest loop
without leaking into deep-parsing territory.
